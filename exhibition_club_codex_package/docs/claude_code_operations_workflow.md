# Claude Code 운영 문서 작업 가이드

이 문서는 Claude Code와 Codex가 회의록, 운영규정, 설문, 회원 공지 및 운영 자료를 안전하게 함께 만드는 절차이다. 현재 사실은 `claude_code_club_context.md`, 저장소 전체 규칙은 루트의 `AGENTS.md`, 공통 역할은 `AI_COLLABORATION.md`를 우선 확인한다.

## 문서를 나눈 이유

- 루트 `CLAUDE.md`는 Claude Code가 세션마다 읽는 짧은 시작 지침이다.
- `claude_code_club_context.md`는 자주 필요한 현재 운영 사실만 담아 `CLAUDE.md`에서 자동으로 불러온다.
- 이 가이드는 운영 문서 작업 때만 읽는 상세 절차라서 매 세션의 기본 문맥을 불필요하게 늘리지 않는다.
- `ai_handoff_template.md`는 Claude와 Codex가 작업 범위와 검증 증거를 같은 형식으로 주고받게 한다.

이 구조는 프로젝트 지침을 `CLAUDE.md`에 두고 `@경로` 형식으로 다른 파일을 불러올 수 있는 [Claude Code 공식 지침 문서](https://code.claude.com/docs/en/memory)의 방식을 따른다. Claude Code는 `AGENTS.md`를 자동으로 읽는 대신, 이 프로젝트의 `CLAUDE.md`가 `@AGENTS.md`를 명시적으로 불러온다.

## 1. 먼저 작업 종류를 정한다

| 작업 종류 | 기본 행동 | 파일 변경 |
|---|---|---|
| 설명·요약 | 원본을 읽고 확인된 내용만 설명 | 하지 않음 |
| 검토 | 오류, 누락, 충돌, 개인정보 위험을 보고 | 하지 않음 |
| 기획 | 구조, 질문, 선택지, 작업 순서를 제안 | 하지 않음 |
| 초안 작성 | 사용자가 요청한 새 문안을 `[가안]`으로 작성 | 별도 파일만 |
| 구현 | 승인된 문안을 실제 파일이나 Google 문서에 반영 | 명시된 대상만 |
| 게시·배포 | 공유 권한, Form 상태, Git 또는 공개 화면까지 반영 | 별도 승인 필요 |

요청이 애매하면 먼저 읽기 전용으로 자료와 충돌을 정리한다. 기존 문서 변경, 설문 공개, 공유 권한 변경, Git 커밋 및 배포는 사용자의 명시적 요청 없이 진행하지 않는다.

## 2. 세션 시작 점검

1. 루트 `CLAUDE.md`, 그 문서가 불러오는 `AGENTS.md`와 `claude_code_club_context.md`를 읽는다.
2. 운영 문서 작업이면 이 가이드와 `ai_handoff_template.md`를 읽는다.
3. `git status --short --branch`로 기존 사용자 변경을 확인한다.
4. 이번 작업의 대상, 제외 대상, 최종 사용자를 한 문장으로 적는다.
5. 사용자가 지정한 Google 문서나 로컬 파일을 직접 읽는다.
6. 각 사실을 `확정`, `운영안`, `시범`, `가안`, `확인 필요`로 분류한다.
7. 외부 상태가 필요한 항목은 확인일과 실제 확인 방법을 기록한다.

## 3. 공통 문서 작성 절차

### 1단계: 자료 목록 만들기

- 정본 문서와 참고 문서를 구분한다.
- 문서 제목, 링크 또는 경로, 확인일, 상태를 기록한다.
- 운영진 내부 시트와 원본 응답은 링크나 내용을 공개용 초안에 넣지 않는다.

### 2단계: 사실과 충돌 확인하기

- 같은 항목의 날짜, 참석자, 비용, 담당자, 승인 상태가 문서마다 같은지 비교한다.
- 전체 규정과 압축본이 다르면 전체 규정을 기준으로 한다.
- 최신 회의 결정이 기존 가이드와 충돌하면 자동 수정하지 말고 승인 필요 항목으로 올린다.
- 근거가 없는 정보는 문맥으로 추측하지 않는다.

### 3단계: 별도 가안 작성하기

- 제목 앞에 `[가안]`을 붙이고 작성일과 참고 자료를 적는다.
- 확정 사항, 제안 사항, 확인 필요 사항을 구획으로 나눈다.
- 회원용 문서는 짧고 쉬운 표현을 쓰되 의무, 비용, 취소, 개인정보 문구를 생략하지 않는다.
- 운영진용 문서는 담당자, 기한 및 다음 확인 지점을 표로 정리할 수 있다. 다만 확인되지 않은 담당자나 기한을 임의로 배정하지 않는다.

### 4단계: 자체 검토하기

- 이름, 일시, 문서 제목 및 링크가 원본과 같은가?
- 공식 규정과 다른 약속을 새로 만들지 않았는가?
- 확정·가안·확인 필요가 명확히 구분되는가?
- 연락처, 원문 대화, 개인별 평가 또는 응답자별 정보가 들어가지 않았는가?
- 회원이 모바일 화면에서 빠르게 읽을 수 있는가?
- 기존 파일과 사용자 변경을 건드리지 않았는가?

### 5단계: 승인과 인계

- 사용자와 운영장이 결정할 항목을 별도로 모은다.
- Claude가 초안을 만들었다면 `ai_handoff_template.md` 형식으로 Codex에게 구현·검증을 인계한다.
- Codex가 구현했다면 실제 파일, Google 문서 ID, Form 응답자 화면, 공유 권한 및 검증 결과를 Claude의 리뷰 대상으로 고정한다.
- 최종 승인 전에는 `[확정]`, `배포 완료`, `응답 수집 중`이라고 단정하지 않는다.

## 4. 문서별 작성 기준

### 운영진 회의록

필수 항목은 제목, 일시, 참석자·초청인, 안건, 논의 내용, 결정 사항, 보류·확인 필요, 후속 조치이다.

- 발언 원문을 길게 옮기지 않고 결정 근거와 결과를 요약한다.
- 합의된 결정과 단순 제안을 분리한다.
- 담당자와 기한은 회의에서 정해졌거나 운영장이 확인한 경우에만 적는다.
- 규정 변경 결정은 어떤 조항에 영향을 주는지 표시한다.

### 운영규정

- 전체본이 법적·운영적 기준이고 압축본은 안내용이라는 관계를 유지한다.
- 목적, 회원·참여, 활동, 비용·취소, 온라인 소통, 사진·개인정보, 상호 존중, 분쟁, 개정 및 시행을 빠뜨리지 않는다.
- 압축 과정에서 책임, 동의, 비용 또는 개인정보 경계를 바꾸지 않는다.
- 시행일이 공란이면 추측하지 말고 승인 질문으로 남긴다.

### 회원 안내

- 회원이 지금 알아야 할 내용과 해야 할 행동을 앞에 둔다.
- 운영진 내부 검토 메모, 관리 링크 및 응답자 정보는 제거한다.
- 링크마다 `정본`, `요약`, `설문`, `참고` 역할을 표시한다.
- 설문이 닫혀 있거나 미검증이면 참여를 독려하는 확정 문구를 쓰지 않는다.

### 운영 설문

- 운영 설문, 작품 선호 투표, 날짜·시간 조사, 최종 참석 확인을 한 설문에 무리하게 섞지 않는다.
- 꼭 필요한 정보만 질문하고 이름 또는 표시 이름은 선택 입력을 기본으로 한다.
- 전화번호, 이메일, 주소, 직장 및 생년월일을 수집하지 않는다.
- 릴레이 인터뷰, 사진 또는 소개 게시 동의는 각각 별도로 받는다.
- 응답 기간, 이용 목적, 열람자, 공개 방식 및 보관 원칙을 설문 첫 화면에 안내한다.
- 배포 직전 응답자 화면에서 질문, 필수 여부, 제출 가능 여부 및 개인정보 안내를 실제로 시험한다.

### 설문 결과

- 응답자 수, 선호 비율, 복수 선택 여부 및 무응답을 함께 표시한다.
- 적은 응답 수에서 개인을 유추할 수 있는 교차 분석은 하지 않는다.
- 원본 응답을 공개 문서나 공개 저장소에 복사하지 않는다.
- 결과는 `확정된 결정`이 아니라 `운영 판단의 근거`로 표현한다.

## 5. 역할과 승인선

### 사용자와 운영장

- 운영 목표와 실제 사실 제공
- 규정 변경, 개인정보 공개 범위 및 최종 문안 승인
- 설문 배포, 회원 공유 및 외부 공개 여부 결정

### Claude Code

- 자료 구조화, 문서 비교, 질문 설계, 별도 가안 작성 및 읽기 전용 리뷰
- 모순, 누락, 불명확한 승인 상태 및 개인정보 위험 표시
- 구현할 내용을 Codex가 바로 실행할 수 있는 인계문으로 작성
- 명시적 요청 없이 Google 원본, Git 상태 또는 공개 화면을 변경하지 않음

### Codex

- 현재 Google 원본과 외부 상태 재확인
- 승인된 로컬 파일 및 Google Docs·Sheets·Forms 구현
- 공유 권한, Form 제출 가능 여부, 문서 읽기 결과 및 공개 화면 검증
- 사용자가 요청한 경우에만 Git 커밋, PR, 병합 및 배포

## 6. 같은 작업 폴더에서 충돌을 막는 방법

- 한 시점에 한 AI만 같은 파일을 수정한다.
- 리뷰를 요청할 때 기준 커밋, 대상 파일 및 현재 diff를 고정한다.
- 리뷰 중인 파일은 리뷰가 끝날 때까지 추가 수정하지 않는다.
- 기존 미커밋 변경은 다른 사람의 작업으로 간주하고 stash, reset, checkout 또는 일괄 포맷하지 않는다.
- 병렬 구현이 필요하면 별도 worktree와 별도 브랜치를 사용한다.
- 문서만 요청한 작업에서 코드, 공개 페이지 또는 배포 설정까지 범위를 넓히지 않는다.

## 7. 파일 이름과 상태 표기

새 로컬 초안을 명시적으로 요청받았을 때 권장 경로는 다음과 같다.

```text
exhibition_club_codex_package/docs/drafts/YYYY-MM-DD-[가안]-문서이름.md
```

- `[가안]`: 운영진 검토 전
- `[검토중]`: 의견 수렴 중이며 아직 배포 금지
- `[확정]`: 사용자와 운영장이 승인한 내용

파일명만으로 확정 상태를 만들지 않는다. 승인 근거와 날짜를 문서 안에도 기록한다. `drafts` 폴더는 실제 초안 작업을 요청받은 때에만 만든다.

## 8. Claude Code에 바로 붙여 넣을 요청 예시

### 현황 파악만 요청

```text
루트 CLAUDE.md와 연결된 동호회 운영 컨텍스트를 읽어줘.
Google 원본과 로컬 파일은 수정하지 말고, 현재 확정 사항·가안·확인 필요 사항을 구분해 보고해줘.
개인정보나 운영진 내부 시트 링크는 출력하지 마.
```

### 새 회의록 가안 요청

```text
운영 문서 작업 가이드에 따라 이번 회의 메모를 기존 운영규정과 비교해줘.
기존 Google 회의록과 운영규정은 변경하지 말고, 별도의 [가안] 회의록 Markdown만 작성해줘.
결정 사항, 제안, 확인 필요, 담당자 미정 항목을 분리하고 마지막에 운영장 확인 질문을 모아줘.
```

### 운영규정 비교 검토 요청

```text
운영규정 전체본을 정본으로 보고 압축본과 회원 안내를 비교해줘.
의미가 달라진 부분, 빠진 의무·비용·동의·개인정보 조항만 우선순위와 근거를 붙여 보고해줘.
파일과 Google 문서는 수정하지 마.
```

### Codex 구현 인계 요청

```text
검토가 끝난 가안을 ai_handoff_template.md 형식으로 Codex에게 인계해줘.
정본 출처, 확정 사실, 변경 대상, 제외 대상, 개인정보 제외 항목, 검증 방법, 운영장 승인 필요 항목을 빠짐없이 적어줘.
```

## 9. 완료 기준

운영 문서 작업은 다음이 모두 충족되어야 완료로 보고한다.

- 요청한 산출물이 각각 존재하고 제목과 상태가 명확하다.
- 사용한 정본과 확인일을 기록했다.
- 확정 사항과 미확정 사항을 분리했다.
- 개인정보와 내부 관리 링크를 제외했다.
- 기존 Google 원본과 무관한 사용자 파일을 변경하지 않았다.
- 외부 구현을 요청받은 경우 문서 ID·링크, 읽기 결과, 공유 권한 및 Form 실제 상태를 각각 검증했다.
- 사용자와 운영장이 결정해야 할 남은 항목을 명시했다.
